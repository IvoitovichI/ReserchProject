# DungeonTrace — правила команды Codex

Этот репозиторий содержит исследовательский Unity-прототип: короткий FP3D roguelite-run, хаб со строительством и воспроизводимая телеметрия для тестирования на реальных участниках.

## Источники истины

Перед работой прочитай только релевантные файлы:

1. `docs/DungeonTrace_CODEX_MASTER.md` — продукт, архитектура, контент, метрики и критерии готовности.
2. `coordination/TASK_BOARD.md` — активные задачи и владельцы.
3. `coordination/DECISIONS.md` — принятые решения; они сильнее старых предположений.
4. `coordination/BLOCKERS.md` и `coordination/NEEDS_FROM_TEAM.md` — блокеры и недостающие входные данные.
5. Локальный `AGENTS.md` своей роли в `agents/<role>/`.

Если документы противоречат друг другу, не угадывай. Зафиксируй конфликт в `coordination/BLOCKERS.md` и запроси решение у оркестратора или пользователя.

## Неподвижные границы прототипа

- Unity, одиночная FP3D-игра для ПК, клавиатура и мышь.
- Небольшой измеримый прототип, а не попытка повторить весь The Binding of Isaac.
- Один короткий игровой цикл: хаб → процедурное подземелье из пресетов → бой/награды/секрет → босс → возврат в хаб → трата валюты.
- Контент MVP: конструктор комнат, генератор подземелья, оружие и урон, 4 типа врагов, 2 босса, секретные комнаты, хаб/строительство, телеметрия/исследовательский режим.
- Исследовательская воспроизводимость важнее визуального масштаба: фиксируй `participant_id`, `session_id`, `build_id`, `condition_id`, `run_id`, `seed` и версию схемы событий.
- Не собирать ФИО, email, голос, видео, точные системные идентификаторы и другие персональные данные без отдельного одобрения протокола исследования.

## Владение зонами

| Роль | Владеет | Не изменяет без handoff |
|---|---|---|
| Game Designer | механики, баланс, референс-анализ, acceptance criteria | C# runtime, схема телеметрии, финальные 3D-файлы |
| Researcher | исследовательские требования, события, переменные, QA данных, анализ CSV/JSON | игровые значения ради «фана», C# кроме согласованного telemetry-контракта |
| 3D Modeler | модели, материалы, LOD/коллизии, asset briefs и art QA | геймплейный код, сцены/префабы интеграции без запроса программиста |
| Programmer | C#, Unity integration, редакторные инструменты, тесты, сборки | научную интерпретацию результатов, незапрошенный редизайн механик |

Оркестратор назначает одного владельца каждому изменяемому файлу. Два агента не редактируют один файл параллельно.

## Обязательный цикл задачи

1. Прочитать задачу, релевантный раздел master-документа и активные решения.
2. Уточнить входы, выходы, ограничения и критерии приемки.
3. Если данных не хватает — добавить запись в `coordination/NEEDS_FROM_TEAM.md` или `BLOCKERS.md`.
4. Выполнить только свою часть.
5. Проверить результат по критериям роли.
6. Заполнить свой файл в `coordination/handoffs/` и обновить статус задачи.
7. Указать измененные файлы, проверки, риски и точный следующий шаг.

## Инварианты интеграции

- ID контента стабильны и не зависят от отображаемого имени: `room_id`, `weapon_id`, `enemy_id`, `boss_id`, `upgrade_id`.
- Настраиваемые данные хранятся в ScriptableObject или другой согласованной data-driven форме; значения не дублируются в коде.
- Телеметрия вызывается через один фасад/сервис, а не из случайных мест проекта.
- События телеметрии append-only в пределах версии схемы; изменение смысла поля требует новой версии.
- Генерация по одному seed должна быть детерминирована в пределах одного `build_id` и набора контента.
- Исследовательский режим отделен от обычного режима и явно показывает согласие, код участника и условие эксперимента.
- Новые зависимости, плагины Unity и облачные сервисы требуют решения в `DECISIONS.md`.
- Не переписывать пользовательские изменения и не удалять ассеты ради устранения конфликта.

## Definition of Done для любой задачи

- Результат соответствует scope и acceptance criteria.
- Нет новых ошибок компиляции Unity и явных ошибок Console.
- Для кода есть EditMode/PlayMode тест либо документированная ручная проверка.
- Для измеримой механики перечислены требуемые telemetry events и проверен пример записи.
- Документы и ID обновлены вместе с реализацией.
- Handoff заполнен так, чтобы следующий агент мог продолжить без устного контекста.

## Коммуникация

- Факты отделяй от гипотез и рекомендаций.
- Ссылайся на конкретные файлы, ID, сцены, префабы и события.
- Не писать «готово», если есть непроверенные предположения; писать «готово с ограничениями» и перечислять их.
- Эскалация: blocker → владелец зависимости → оркестратор → пользователь, если решение влияет на исследовательскую валидность, срок или scope.
