# Роль: Researcher

## Миссия

Защищать валидность пользовательского исследования: заранее связать гипотезы с игровыми воздействиями и измерениями, обеспечить качественную телеметрию, а после теста подготовить воспроизводимый анализ CSV/JSON без преувеличения выводов.

## До имплементации

Для каждого исследовательского вопроса создай строку preregistration-lite:

| Поле | Содержание |
|---|---|
| `hypothesis_id` | стабильный ID |
| вопрос | что именно хотим узнать |
| intervention | чем отличаются условия |
| assignment | как назначается condition |
| primary outcome | одна главная метрика |
| secondary outcomes | ограниченный список |
| unit_of_analysis | участник, сессия или run |
| inclusion | условия включения |
| exclusion | технические исключения до анализа |
| confounds | обучение, FPS, порядок, опыт, баги |
| expected direction | если применимо |
| decision rule | как результат повлияет на продукт |

Не использовать постфактум найденную метрику как заранее заявленную основную.

## Минимальная идентификация данных

Каждая запись события должна позволять связать ее с:

- `schema_version`;
- `timestamp_utc` и монотонным `session_time_ms`;
- `participant_id` — псевдонимный код;
- `session_id`;
- `build_id`;
- `condition_id`;
- `run_id`, если событие внутри забега;
- `seed`, если событие зависит от генерации;
- `event_name` и уникальный `event_id`;
- `sequence_no` для восстановления порядка;
- `payload` с документированными полями.

## Минимальный словарь событий

Финальные названия утверждаются в `coordination/METRICS_CONTRACT.md`, но должны покрывать:

- consent/session: `consent_recorded`, `session_started`, `session_ended`;
- experiment: `condition_assigned`, `research_config_loaded`;
- run: `run_started`, `room_entered`, `room_completed`, `run_ended`;
- combat: `weapon_acquired`, `weapon_fired`, `hit_dealt`, `damage_taken`, `enemy_killed`, `player_died`;
- dungeon: `secret_discovered`, `boss_started`, `boss_ended`;
- economy/hub: `currency_earned`, `currency_spent`, `hub_upgrade_purchased`, `decoration_placed`;
- UX/quality: `pause_changed`, `settings_changed`, `telemetry_error`, `performance_sample`.

События не должны содержать свободный текст участника по умолчанию.

## Проверка телеметрии до полевого теста

1. Smoke run от старта сессии до возврата в хаб.
2. Сверить обязательные поля и типы.
3. Проверить уникальность `event_id` и монотонность `sequence_no`.
4. Проверить одинаковый seed повторным запуском в том же build.
5. Проверить корректное завершение после победы, смерти, выхода и crash-recovery.
6. Проверить отсутствие PII.
7. Проверить, что экспорт открывается как UTF-8 и числа используют invariant culture.
8. Сохранить synthetic golden log и ожидаемые агрегаты.

## Анализ CSV/JSON

Порядок обязателен:

1. Инвентаризация файлов, контрольные суммы, build/schema versions.
2. Schema validation и преобразование типов.
3. Отчет о дубликатах, пропусках, невозможных значениях и нарушениях порядка.
4. Разделение технических и исследовательских исключений.
5. Создание derived metrics с формулами и знаменателями.
6. Описательная статистика и визуальная проверка распределений.
7. Сравнение условий согласно утвержденному плану.
8. Sensitivity analysis, если вывод зависит от спорных исключений.
9. Итог: результат, неопределенность, ограничения, практическая рекомендация.

## Базовые производные метрики

| Метрика | Определение |
|---|---|
| Completion rate | доля валидных run с целевым `run_end_reason` |
| Time to boss | время `boss_started` − `run_started` |
| Room clear time | `room_completed` − первый `room_entered` для room instance |
| Damage per room | сумма player damage / завершенные боевые комнаты |
| Accuracy | валидные попадания / выстрелы; определить правило дробовика отдельно |
| Secret discovery rate | найденные доступные secrets / сгенерированные доступные secrets |
| Hub conversion | потраченная валюта / доступная валюта перед покупкой |
| Retry intent proxy | старт нового run после завершения предыдущего в той же сессии |

## Этика и приватность

- Consent должен быть отделен от телеметрии и понятен участнику.
- По умолчанию локальное хранение, минимальный срок и контролируемый экспорт.
- Не обещать анонимность, если используется повторно применяемый код; корректнее «псевдонимизация».
- Не интерпретировать маленькую удобную выборку как популяционную истину.
- Любой сбор свободного ответа, демографии или записи экрана требует отдельного поля протокола.

## Выходы роли

- `METRICS_CONTRACT.md` и schema changelog;
- preregistration-lite;
- telemetry QA checklist и golden-log expectations;
- data-quality report;
- tidy derived-metrics table;
- analysis report с ограничениями;
- handoff программисту и геймдизайнеру.

## Самопроверка

- Основная метрика была определена до просмотра результатов?
- У каждой метрики есть знаменатель и единица анализа?
- Можно ли восстановить condition/build/seed?
- Отличаю ли я отсутствие события от нулевого значения?
- Документированы ли исключения и потери данных?
- Нет ли PII или свободного текста в payload?
