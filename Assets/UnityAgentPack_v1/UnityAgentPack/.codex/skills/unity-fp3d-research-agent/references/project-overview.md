# Project overview

## 1. Назначение

Dungeon Trace — управляемая экспериментальная игра на Unity для сбора поведенческой телеметрии. Она должна быть достаточно простой для коротких сессий, но предоставлять наблюдаемые выборы в исследовании пространства, бою, использовании ресурсов и персонализации хаба.

Исследовательская логика строится вокруг трёх принципов:

1. Поведение измеряется через игровые действия, а не назначается по одному событию.
2. Сравниваются нормализованные признаки и устойчивые тенденции, а не только абсолютные counts.
3. Main study проводится на фиксированных правилах; классификация выполняется offline и не изменяет опыт участника.

## 2. Игровой цикл

`Hub → briefing/tutorial → deterministic dungeon → rooms and choices → boss/outcome → rewards → hub spending → next assigned run`.

Один забег: ориентировочно 10–15 минут. Основной протокол может использовать два забега на участника с counterbalanced seed order и отдельную короткую фазу хаба.

## 3. MVP

- First-person 3D CharacterController без jump/crouch.
- 12–16 проверенных room prefabs, собранных graph generator по seed.
- 4 оружия: надёжный hitscan, spread hitscan, точный/заряжаемый вариант и медленный projectile/AOE.
- 4 архетипа врагов с разными читаемыми угрозами.
- 2 босса с детерминированными фазами и телеграфами.
- Reward/shop room, секретные комнаты и подсказки, читаемые с высоты глаз.
- 12 пассивных предметов с ограниченными и прозрачными modifiers.
- Fixed-slot hub: функциональные улучшения и косметические элементы за валюту.
- Local JSONL telemetry, session manifest, validator и export.
- Режимы `ResearchObservation`, `Pilot`, `Sandbox`.

## 4. Не входит в MVP

- Multiplayer, live service, monetization и cloud account.
- Runtime procedural geometry; используются только проверенные room prefabs.
- Jump, crouch, climbing и сложная vertical traversal.
- Удалённая отправка телеметрии и online dashboard.
- Свободная physics-based расстановка мебели.
- Реальная адаптация игры по типу игрока в main study.
- ML inference внутри игрового цикла.

## 5. Исследовательские наблюдения

| Область | Наблюдаемые действия | Примеры нормализации |
| --- | --- | --- |
| Exploration | ветви, секреты, возвраты, dwell, направление взгляда | на число доступных ветвей, secrets и время |
| Combat | попадания, дистанция, dodge, урон, оружие | на shots, encounters, enemy opportunities |
| Resources | покупка, пропуск, сохранение валюты, предметы | на число offers и доступную валюту |
| Hub | выбор функционального/косметического, placement, undo | на число доступных слотов и items |
| Skill/confounds | aim error, clear time, deaths, tutorial errors | используются как covariates, не как мотивация |

Не выдавать единый тип игрока по одному событию. Предпочитать continuous profile vector, confidence/uncertainty и устойчивость между забегами.

## 6. Режимы

### ResearchObservation

Фиксированные правила, назначенный seed, стандартизированное состояние профиля, отключённая адаптация, полный event stream. Основной режим сбора.

### Pilot

Используется для проверки UX, сложности, motion discomfort, seed comparability и качества данных. Баланс может изменяться между версиями, но не внутри сессии скрытым образом.

### Sandbox

Инструменты разработчика: выбор seed/room/weapon/item, бессмертие, ускорение, просмотр событий. Sandbox sessions обязательно маркируются и не смешиваются с main-study data.

## 7. Термины

- **Seed** — вход детерминированного генератора.
- **Content version** — версия контента и баланса, влияющих на возможности и метрики.
- **Schema version** — версия смысла и структуры телеметрических событий.
- **Opportunity** — доступная игроку возможность совершить действие; нужна для нормализации.
- **Condition** — назначенное экспериментальное условие.
- **Manifest** — неизменяемое описание session/build/settings/assignment.
- **Run** — один полный или прерванный заход в подземелье.
- **Room definition** — authored data с ID, sockets, tags, budget и ссылкой на prefab.
- **Stable ID** — постоянный машиночитаемый идентификатор, не зависящий от имени asset или сцены.

## 8. Критерий успеха прототипа

Прототип готов к main study, когда назначенные seeds воспроизводимы и сопоставимы, комнаты не создают softlock, FPS-управление читаемо и комфортно, события валидируются и восстанавливаются после штатного/аварийного завершения, а исследователь может связать данные с условием без хранения личности участника.
