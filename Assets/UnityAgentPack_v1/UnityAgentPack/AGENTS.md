# Dungeon Trace — правила для AI-агента

Эти инструкции действуют для всего Unity-репозитория. Более близкий к файлу `AGENTS.md` может уточнять их для конкретного модуля.

## Контекст проекта

Dungeon Trace — короткая одиночная FP3D roguelite-игра для исследования поведения игроков. Игрок проходит детерминированное подземелье из комнат-пресетов, использует найденное оружие, сражается с четырьмя типами врагов и одним из двух боссов, ищет секреты и тратит валюту на развитие личного хаба.

Главная ценность сборки — не объём контента, а воспроизводимый эксперимент и корректная телеметрия.

## Перед изменением

1. Изучи реальные файлы, Unity-версию в `ProjectSettings/ProjectVersion.txt`, используемые packages и существующие тесты.
2. Найди владельца поведения: definition, runtime service, presentation или telemetry. Не дублируй ответственность.
3. Проверь, меняет ли задача игровой опыт, доступные игроку возможности, seed determinism, формат данных или исследовательский протокол.
4. Для проектных задач используй навык `.codex/skills/unity-fp3d-research-agent/SKILL.md` и только необходимые references.

## Обязательные ограничения

- Не изменяй Unity/package/render-pipeline версии без прямой необходимости и согласования.
- Не редактируй `.meta` вручную и не регенерируй GUID существующих assets.
- Не перемещай и не переименовывай assets без сохранения их `.meta`.
- Не коммить `Library/`, `Temp/`, `Logs/`, `Obj/`, пользовательские IDE-файлы и локальные исследовательские выгрузки.
- Не добавляй PII участников в логи. `participant_id` должен быть выданным исследователем псевдонимом.
- Телеметрия не должна влиять на результат боя, генерацию, награды или выбор контента.
- В `ResearchObservation` запрещена скрытая адаптация. Сравниваемые условия используют контролируемые seed и версии контента.
- Стабильный ID обязателен для комнаты, двери, зоны, предмета, оружия, врага, босса и clue. Имя GameObject не является ID.
- Изменение геометрии, spawn layout, баланса, loot или поведения, влияющего на метрики, требует оценки необходимости нового `content_version`.
- Изменение смысла события или его обязательных полей требует нового `schema_version`.

## Архитектурные правила

- Направление зависимостей: `Definitions/Domain → Runtime systems → Presentation`; `Telemetry` подписывается на события и не вызывается из чистой доменной логики напрямую.
- Plain C# используется для детерминированных правил и преобразований; `MonoBehaviour` — для Unity lifecycle; `ScriptableObject` — для неизменяемых authored definitions.
- Не использовать `FindObjectOfType`, `GameObject.Find`, строковые сообщения и глобальный service locator как обычный способ связи.
- Не создавать новый Singleton, пока не доказан единственный lifecycle и невозможность явной зависимости.
- Ввод преобразуется в команды. Runtime-логика не должна напрямую опрашивать клавиши в разных системах.
- Камера задаёт точку прицеливания. Projectile выходит из muzzle, но направляется к camera aim point после проверки близкого препятствия.
- События gameplay должны быть типизированы; подписки обязательно освобождаются симметрично.
- Не хранить runtime-состояние в definition assets.

## Рабочий цикл

1. Сформулируй наблюдаемый результат и acceptance criteria.
2. Сделай минимальный вертикальный срез от definition до runtime и теста.
3. Добавь телеметрию только для осмысленного действия или перехода состояния.
4. Проверь отсутствие аллокаций и логирования в горячих циклах.
5. Запусти доступные EditMode/PlayMode tests, compile/build checks и валидаторы контента.
6. В итоговом отчёте перечисли изменённые файлы, результат, проверки, непроверенные части и влияние на версии данных.

## Definition of Done для любой задачи

- Проект компилируется без новых warnings, связанных с изменением.
- Поведение не зависит от FPS, если это не visual-only эффект.
- Нет новых scene searches, неявных строковых ID и утечек event subscriptions.
- Ошибочные конфигурации завершаются понятной диагностикой, а не случайным `NullReferenceException`.
- При затронутой телеметрии событие сериализуется, проходит validator и не содержит PII.
- При затронутой генерации одинаковый seed остаётся воспроизводимым.
- Документация и тесты обновлены настолько, насколько изменился публичный контракт.
